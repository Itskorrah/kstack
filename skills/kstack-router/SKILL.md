# KStack router

Apply this workflow to substantial code changes. For trivial edits, use the simplest safe path and avoid a multi-agent ceremony.

1. Inspect repository instructions, current source, build commands and outstanding work; preserve unrelated user edits.
2. Identify the actual target language, framework, environment, acceptance criteria and risk. Use an available project profile or `kstack route` to obtain suggestions.
3. Choose **one** lead development workflow, normally Evolve when installed and applicable. Do not invoke overlapping orchestrators or claim an external tool is installed based on a catalogue entry.
4. Load specialist guidance only when its description matches the task: architecture/independent review, UI/accessibility, framework-specific performance, browser tests or documentation.
5. Write explicit implementation boundaries, acceptance cases and a short test plan. Parallelise only truly independent work with owned file boundaries.
6. Implement complete vertical slices, verify negative and positive paths, measure changes, and keep verified output separate from untested claims.
7. Use `kstack-verify` before substantial delivery and `kstack-ship` only when delivery was authorised in the conversation.
8. Record repeated problems as specific proposed improvements to KStack; never silently self-modify trusted instructions during a code task.

If a skill is unavailable or an environment is blocked, do the feasible work directly, note the blocker and continue. Tool and model role preferences are advisory, not a guarantee of effective model identity.
